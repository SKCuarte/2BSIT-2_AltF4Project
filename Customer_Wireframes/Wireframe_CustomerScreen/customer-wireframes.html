Scope and flow

The wireframes cover the five things Issue #110 asks for: list, search/filter controls, create/edit forms with the payment-terms field, and soft-delete/restore. A detail view is included because the issue names it in its objective.

Customer list→ Search / filter→ Customer detail→ Edit form→ Save → list (toast)
Customer list→ Add customer→ Create form→ Save → list (toast)
List / detail→ Deactivate→ Confirm→ Blocked: related records Inactive (kept)
Status filter: Inactive→ Restore→ Confirm→ Active again
Grounded in the issue and related tickets Customer list search and status/payment-term filters and active-only default come from S2-DEV-01 (#90). Create/edit with payTerms validation comes from S2-DEV-02 (#91). Soft delete to Inactive, blocked deletion when child records exist, and restore come from S2-DEV-03 (#92). Field names and limits come from db/migrations/001_hope_base_structure.sql and the unmerged active-view migration.
Read the notes on each screen Several points are inconsistent between the issue, the database, and the Sprint 1 handoff (field set, payTerms naming, restore rights, hard-delete copy). They are flagged on the relevant screen and collected in the deliverable document.

1 · Default filter is Active S2-DEV-01 (#90) says the list displays active customers. Inactive records stay reachable through the status filter so Restore is possible.
Row actions follow rights Add customer needs Add Customer; Edit needs Edit Customer; Deactivate needs Delete Customer. S2-DEV-01 requires each button to render only when the matching right is held.
Column set needs a decision The Sprint 1 handoff lists Customer columns as Name, Email, Phone, Status. The database has customer_id, customer_name, customer_address, terms, status, stamp — no email or phone. This wireframe follows the database because the issue requires payTerms, which only exists there.
View permission is not in the rights catalogue #90 mentions a “Customer view permission”, but the 36-right catalogue only defines Add, Edit and Delete Customer. See Open question 1.

06 · Soft delete (deactivate)

Soft delete sets Status to Inactive. It never removes the row. If related sales exist, the action is blocked.

06

Deactivate confirmation

Confirmation dialog, per the handoff’s confirm-dialog rule

!

Deactivate Acme Corporation?

The customer will be marked Inactive and hidden from the active list. The record is kept and can be restored.

Existing sales records are not changed.

Wording is deliberate“Deactivate” and “can be restored” match the soft-delete behaviour in #92 and the CUSTOMER status comment. The Sprint 1 prototype’s “This cannot be undone” copy describes a hard delete and must not be reused.
Status valueThe database CHECK allows only Active or Inactive. “Inactive” is the soft-delete state.
06b

Deactivate blocked by related records

Child-record integrity check

!

This customer can’t be deactivated

Acme Corporation has related sales records. Resolve or reassign those records first, then try again.

The customer stays Active. No data is changed.

Grounded in #92 and the schema#92 requires deletion to be blocked when restricted child records exist. SALES.customer_id references CUSTOMER with ON DELETE RESTRICT.
Which records, and how to resolve themNeither the issue nor the references define whether the dialog should list the blocking sales or offer a jump to them. No list is shown (Open question 6).

⚑

Open questions carried into review

Full detail is in S2-UIX-01-deliverables.md

  1. Does a Customer view right exist, or is list access implied by any Customer right?
  2. Which right authorises Restore — Delete Customer or a new one?
  3. Is Customer ID typed by staff, generated, and editable after creation?
  4. Is payTerms required, and what CHECK values apply? Is the column renamed from terms?
  5. What belongs on the detail view, and should it list related sales?
  6. Should the blocked-deactivate dialog name or link the related records?
  7. Which column set is approved: Name/Email/Phone/Status (handoff) or ID/Name/Address/Terms/Status (database)?
  8. Is pagination required? It appears in User Management but not in the Customer tickets.
