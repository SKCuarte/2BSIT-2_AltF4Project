## Code currently prepared

- The authenticated `GET /api/admin/users/[id]/rights` route loads the active catalogue and assigned Active rows.
- The `POST` route validates a bounded, duplicate-free right-ID list, authenticates the Admin/Superadmin server-side, and returns `409 policy_pending` before any mutation RPC can be called.
- The policy decision is isolated in `web/lib/rights-management-policy.mjs` and currently denies every write. The write service also checks that boundary independently.
- A pure planner computes grant and soft-revoke differences and rejects duplicate Active assignments. A separate local-selection helper powers the module/global draft controls. Neither helper writes to the database.
- No `manage_user_permissions` RPC definition is present in the tracked repository. Its existence in the live database is unverified; this implementation does not rely on it while policy approval is pending.

### Confirmed audit ID handling

Supabase inspection supplied for this task confirms:

- `audit_log.id` is `GENERATED BY DEFAULT AS IDENTITY` with its own associated sequence.
- `audit_log.audit_id` is `GENERATED ALWAYS AS IDENTITY`, its own associated sequence, and the canonical primary key.
- Omit **both** `id` and `audit_id` from each audit insert. Let their existing identity definitions generate values; do not assume the values match or create/alter sequences.
- `user_permission` currently has no audit trigger. Choose either the explicit audit insert in the same transaction or a reviewed trigger, never both.
- `audit_user()` checks transaction-local `app.current_user`, then `app.username`, then falls back to `system`.

The identity behavior is confirmed; required audit payload columns and the complete insertion behavior still need DB Admin review.

## Schema drift to reconcile

The reported live schema and repository migrations differ:

1. Live `app_user.id` and `user_permission.user_id` are UUID; [migration 003](../db/migrations/003_user_management.sql) defines BIGINT IDs and a composite primary key for `user_permission`.
2. Live `user_permission` has no unique constraint. Do not assume the migration's uniqueness guarantees apply to the live database.
3. Live `audit_log` has two identity columns as described above.
4. The supplied DB Admin note refers to a migration 008 that defines `audit_log.id` as `GENERATED ALWAYS`. However, the currently tracked [008_protect_last_superadmin.sql](../db/migrations/008_protect_last_superadmin.sql) does not define `audit_log`; it contains last-Superadmin protection. The DB Admin should identify the exact migration file/version being compared before reconciliation.

Do not apply the repository baseline blindly to a hosted project. The database guide requires comparing the public schema before migrations; use a fresh, separate Development project and a reviewed schema plan.
